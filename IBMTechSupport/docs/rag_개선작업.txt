1. 프로젝트의 목적과 전체 구조
============================================================
목표: IBM TechQA 기반 기술지원 질문에 대해, 검색한 IBM 기술 문서를 근거로 답변하고 근거 부족 시 답변을 유보하는 LLM/RAG 시스템 구성.

전체 처리 흐름
원본 QA 및 근거 문서
  -> 필드/중복/레이블 검증
  -> 데이터 전처리 및 Train/Validation/Test 분할
  -> Base Model 추론 및 기준 성능 평가
  -> 문서 청킹/인덱싱/임베딩/검색
  -> (별도) LoRA/QLoRA 학습 및 성능 비교
  -> RAG 검색 결과의 근거 선별 및 프롬프트 구성
  -> LLM 답변 생성 / 유보 결정 / guardrails 결과 저장
  -> Judge에서 Claim 추출 -> IBM 근거 구절 비교
  -> 자동 승인 또는 검토 필요 표시
  -> 사람 검토 기반 Judge 보정(미완료)

2. 원본 데이터 확보 및 검증
============================================================
[설계/논의] IBM TechQA 관련 데이터 기반으로 개발 시작.
- 원본 질문/정답 중심 필드: id, question, answer, is_impossible, contexts.
- contexts 내부 문서는 filename, text 등의 자료를 포함할 수 있음.
- TRAIN_*, DEV_*와 같은 ID 접두어로 구간을 구별하는 설계를 사용.

[설계/논의] 데이터 점검 항목
1) 필수 필드 존재 및 타입 검증
2) QA ID 중복 검출
3) 질문/정답의 완전 일치 중복 검출
4) 공백/유니코드 등 정규화 이후 중복 검출
5) 답변 가능 여부(is_impossible)와 answer/contexts 정합성 검사
6) 문서 filename 및 본문 텍스트 유효성 검사
7) 데이터 분할 간 중복·누수 확인

[확인 필요] 각 데이터 검증 함수의 최신 구현, 누락/중복 건수, 정제 전후 레코드 수는 이번 자료에서 재검증하지 못함.

[설계/논의] 원본 정답 레이블(qa answer)과 RAG 검색 문서(text)는 구분한다. 질문/정답 레코드를 그대로 검색 인덱스에 넣으면 평가 누수 위험이 있다.

4. 검색(Retrieval) 및 RAG 구축
============================================================
[확인] dense_search.py를 사용한 Dense Search 관련 작업과 BM25, Hybrid Search(RRF) 코드가 이전 대화에서 다뤄짐.
- Dense: 질문/문서 임베딩을 이용한 검색.
- BM25: 어휘 일치 기반 검색.
- Hybrid: BM25 + Dense 후보를 결합해 순위를 생성.
- 과거 공유한 Hybrid 코드 설정값: CANDIDATE_K=50, RRF_K=60, TOP_K=10.
  (당시 코드 설정으로, 현재 확정 운영 설정이라고 단정할 수 없음.)

[설계/논의] 검색 품질은 정답 문서 히트율, 청크 선택, 재현 가능한 인덱스와 설정으로 검증한다.
[확인 필요] 현재 인덱스 버전, 청킹 전략, 전체 Recall@K/MRR/Hit@K 최종 수치, 모든 모델별 비교표는 소스/결과 확인 필요.

5. '검색한 정답/근거 문서를 프롬프트에 전달하는 방식'의 변화
============================================================
용어 먼저 구별
- 정답 레이블: 데이터셋에 있는 reference answer.
- 검색 후보 문서: retriever가 반환한 retrieved_documents.
- 사용된 근거 청크: guardrails.used_chunk_ids로 식별되는 문서.
- 답변 생성용 프롬프트: RAG 모델이 IBM 문서 내용을 받는 입력.
- Judge 검증용 프롬프트: 생성된 답변의 주장과 IBM 근거를 대조하는 별개의 입력.

[설계/논의] 초기 RAG 프롬프트 방식
질문과 검색 Top-K 문서를 다음과 같이 함께 제공하는 구조로 설계됨.
  질문
  Reference documents:
  [1] document_id + 검색 문서 본문
  [2] document_id + 검색 문서 본문
  ...
  문서 근거로 답하고 근거 부족 시 유보
검색된 문서는 '참조 후보'이지, 반드시 정답이라고 간주하지 않음.

[확인] 현재 v4 출력에 대해 Judge가 참조하는 필드와 선별 로직(judge_quality.py)
- selected_docs(record): retrieved_documents에서 guardrails.used_chunk_ids에 해당하는 청크만 추출.
- evaluation_docs(record): 일반 답변은 selected_docs(record)를 평가 근거로 사용.
- 답변이 INSUFFICIENT_INFORMATION이면 retrieved_documents의 상위 10개까지 확인.
  이유: 사용 청크가 0개라는 사실만으로 유보가 정당하다고 승인하는 오류를 방지.

[확인] Judge v3.3~v3.6의 근거 전달 방식 변화
- 기존의 '모델에게 근거 인용문을 직접 쓰도록 요청'하는 방식은 원문이 아닌 인용을 만들거나 잘못된 문서 ID를 내는 위험이 있음.
- Evidence-first 방식에서는 Python이 IBM 문서 본문에서 연속된 실제 구절을 추출하고, E1/E2/... 등 근거 ID를 부여.
- 주장별로 연관 근거를 선정(코드 상 최대 5개 근거 구절)해 Judge LLM에 제공.
- Judge는 SUPPORTED / CONTRADICTED / NOT_FOUND, evidence_id, reason을 JSON으로 출력.
- 프로그램이 evidence_id를 원래 문서 본문과 매핑하므로 Judge가 임의 인용문을 생성할 필요 없음.
- 주요 경로, 기술 명령, 숫자 조건, 실제 조치가 근거 구절과 맞는지도 검증.
- 불명확한 판정은 REVIEW_REQUIRED로 분류하고 자동 승인하지 않음.

[확인 필요 / 중요]
- 'RAG 생성 모델에 Top-K 문서 전체를 넣던 방식에서 현재 정확히 어떤 문서/청크만 프롬프트에 넣도록 수정했는지'는 실제 생성 프롬프트 조립 소스를 이번에 직접 확인하지 못함.
- 위 v4의 used_chunk_ids는 출력 기록과 Judge 입력 선별 방식에 대한 사실이며, 이 사실만으로 RAG 생성 프롬프트의 변경 전후 소스(diff)를 확정하지 않음.
- 다음 작업에서 RAG v4 프롬프트 구성 함수와 과거 버전 소스를 비교해 파일명/함수명/변경 이유를 이 문서에 보완할 것.

[확인] Judge 평가 흐름
1) RAG 결과의 prediction/question 및 근거 문서 읽기.
2) 일반 답변은 used_chunk_ids의 문서, 유보 답변은 검색 상위 10개 문서로 검증 범위 지정.

7) 판정 충돌/근거 부족/출력 오류는 자동 승인하지 않음.
8) Claim 판정값을 사용해 rubric 점수와 auto_pass/REVIEW_REQUIRED 생성.
9) 모델 판정의 의미적 정확도는 별도 사람 검토가 필요.

[확인] 수정 흐름

    - 동일 QA ID의 Judge와 사람 판정을 짝지어 Precision / Recall / False Approval Rate / Kappa 계산.
    - 코드의 기존 calibrate()는 judge_status != OK인 사례를 제외하므로,
      8건 REVIEW_REQUIRED를 빼고 계산한 수치를 전체 20건 성능으로 오해하지 말 것.
    - Human review coverage, auto-approval coverage, review-required rate를 별도 보고.
    - 충분한 검토 건수/긍정·부정 사례가 쌓이기 전에는 CI enforce Gate를 활성화하지 않음.

[4] 원인 분류 및 필요 시 수정
    - False Approval: 실제 오답인데 승인한 사례.
    - False Rejection: 정답인데 거부한 사례.
    - Review Required: 판정이 모호해 자동화 범위 밖으로 보낸 사례.
    - 원인을 source retrieval / 청크 선별 / 프롬프트 구성 / 모델 의미 판단 / 파서 및 정책으로 분리.
    - 반복되는 원인이 실증될 때만 통합 수정 및 회귀 테스트 추가.

[5] RAG 생성 프롬프트 검증 및 개발 이력 보완
    - 검색 Top-K 중 어떤 문서를 LLM에 실제로 전달하는지 로그/소스로 확인.
    - 근거 ID/문서 제목/본문/출력 시 저장한 used_chunk_ids가 서로 일치하는지 확인.
    - 이전 버전과 v4의 프롬프트 구성 함수 diff 및 변경 이유를 문서화.
    - 개발용 Validation 변경을 고정한 뒤 독립 Test 평가 계획 수립.

IBMTechSupport/evaluate_results/106/judge_quality/rubric_judge_v36.jsonl

사람 검토용 새 파일을 만들기 전 주의:
- judge_quality.py prepare는 자체 balanced_sample을 뽑는다.

- 기존 human_review_template.csv를 덮어쓰지 않도록 출력 경로를 별도 지정한다.

같은 ID의 사람 검토 CSV 준비 후 실행할 calibrate 예시:
python IBMTechSupport/scripts/evaluate/judge_quality/judge_quality.py calibrate --review-csv IBMTechSupport/evaluate_results/106/judge_quality/human_review_v36.csv --judge-jsonl IBMTechSupport/evaluate_results/106/judge_quality/rubric_judge_v36.jsonl --output IBMTechSupport/evaluate_results/106/judge_quality/calibration_metrics_v36.json

(예시의 human_review_v36.csv는 아직 생성되지 않았음. 먼저 20건을 정확히 매핑해 준비해야 함.)
