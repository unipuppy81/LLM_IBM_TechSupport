IBM 기술지원 QA | Strict RAG의 과도한 답변 거부 개선 실험
2026-11-28 · Qwen2.5-1.5B-Instruct

결론
  val_106에서 focused 재판정이 기존 Strict가 거부한 세 문항을 Judge 정답으로
  복구했다. 답변 가능 77건의 정답은 25→28건(32.5%→36.4%), 오거부는
  48→45건이 됐다. 답변 불가능 29건에 대한 응답은 6건으로 유지됐다.
  네 가지 재판정 방식 중 성공 기준을 충족한 것은 focused 하나였다.
  같은 106건에서 재실행 결과가 일치했다. 새 미사용 평가 세트의 성능은 미측정이다.


1. 왜 모델 재학습에서 근거 판정으로 실험 대상을 바꿨나

LoRA 설정 변경, 학습 데이터 정제, DPO, DAPT+SFT를 시도했지만 기술 정답이
일관되게 늘지 않아 LoRA/QLoRA 실험을 종료했다. 아래는 당시 test_clean.json
120건의 저장된 1차 평가 결과다. 정답과 오거부의 분모는 답변 가능 80건,
불가능 문항 응답의 분모는 40건이다.

  구성                          Judge 정답    오거부    불가능 문항 응답
  Base                              41            5              34
  Base + LoRA                       32            0              40
  Base + QLoRA                      32            0              40
  Base + Stage3 Strict RAG          20           47              11
  RAG + Context LoRA                11           61               9
  RAG + Context QLoRA               10           67               8

Base에 Strict RAG를 적용하면 불가능 문항 응답이 34건에서 11건으로 줄었지만,
답할 수 있는 질문도 47건 거부했다. 반대로 Base + LoRA/QLoRA는 오거부가
0건이어도 Base보다 정답이 적었다. 이 결과를 보고 후속 실험의 성공 기준을
“답변 가능 문항의 Judge 정답이 늘고, 불가능 문항 응답은 늘지 않을 것”으로
정했다. 목표 설정에 사용한 120건은 1차 결과로 보존했다. 후속 비교에는
val_106.json만 사용했고, 추가 학습은 하지 않았다.


2. 무엇을 원인 후보로 보았고, 어떤 기준선과 비교했나

이전 val_106 진단에서 답변 가능 77건 중 52건을 Strict가 거부했다. 그중
18건의 실제 검색 청크를 검토했을 때, 11건에는 답할 근거가 있었는데도
Evidence Judge가 Top5와 Top10에서 모두 NO를 냈다. 이는 검토한 18건에 대한
관찰이다. 52건 전부에 충분한 근거가 있었다고 볼 수는 없다.

기존 진단 로그에는 불가능 29건의 결과가 없어 106건 전체를 다시 평가했다.
일반 v3 설정의 기본 검색기는 reranker였지만 진단에서는 Stage3를 사용했다.
또한 Stage3 런타임이 인접 청크를 붙이는 반면 진단은 원래 청크 본문을
사용했다. 비교 양쪽 모두 진단과 같은 방식으로 문항별 Top10을 한 번 검색해
저장하고, 같은 순위와 원문을 읽도록 했다.

과거에 검토한 18문항의 Top5 청크 90개는 이번 캐시와 파일명·순위·본문이
모두 일치했다. 답변 가능 77건만 따로 검색해도 전체 106건을 검색했을 때와
77건 모두 Top10이 같았다. 다만 이번 오거부는 48건으로 과거의 52건과 달랐다.
차이의 원인은 확정하지 못했다. 개선 폭은 이번 기준선인 정답 25/77,
오거부 48/77, 불가능 문항 응답 6/29에서 계산했다.

공통 실행 규칙
  · 기존 Evidence Judge가 실제 Top5와 Top10에서 모두 NO인 경우에만
    최종 거부 직전에 재판정을 한 번 적용했다. 해당 문항은 총 68건이었다.
  · 재판정은 질문과 실제 Top5 청크를 사용했다. 문항 ID, 진단 정답,
    답변 가능 여부로 통과 대상을 지정하지 않았다.
  · 통과하면 원래 Top5와 기존 프롬프트로 생성하고, 기존 Grounding Verifier가
    응답을 검증했다. 마지막에 별도 기술 정답 Judge가 참조 답변과 비교했다.
    따라서 근거 검사 통과, 최종 응답, 기술 정답은 서로 다른 측정값이다.


3. 무엇을 바꿨고, 어디에서 실패하거나 성공했나

실험 1 | 모델이 원문을 직접 인용하는 방식 (verbatim) — 실패
  근거가 충분한데도 단어 하나로 NO가 나온다면, 요구사항별로 근거를 제시하게
  했을 때 누락된 답을 찾을 수 있다고 보았다. 모델이 요구사항, 제품·버전·환경
  조건, 청크 ID와 인용문을 JSON으로 출력하게 하고, 코드가 지정 청크에 실제
  인용문이 있는지 검사했다. 예비 실행에서 정상 JSON을 Markdown 코드 블록으로
  감싸는 현상을 확인해 단일 코드 블록을 읽도록 수정했다. 예비 17건은 집계에서
  제외하고 최종 파서로 106건 전체를 다시 실행했다.
  결과는 68건 재판정, 0건 통과였다. 모델이 YES를 낸 30건 중 17건은 지정한
  청크와 인용문이 맞지 않았고, 13건은 질문과 인용문에서 적용 조건을 확인할 수
  없었다. 나머지는 근거 부족·불확실 26건, JSON 오류 12건이었다.
  최종 정답은 25건 그대로였다. 다음 실험에서는 인용문 복사를 코드에 맡겼다.

실험 2 | 번호를 붙인 원문 구간 선택 (passages) — 실패
  질문과 청크의 적용 조건을 먼저 대조한 뒤, 모델이 필요한 원문 구간 번호를
  선택하게 했다. 청크 ID와 인용문은 코드가 선택된 구간의 시작·끝 위치에서
  복원했다. 68건 중 53건은 조건에 맞는 청크를 찾지 못했다. 2건은 재판정을
  통과해 답변까지 생성했지만 기존 Verifier가 둘 다 거부했다. 나머지 13건은
  근거 부족·불확실 4건, JSON 오류 7건, 선택 형식 또는 구간 번호 오류 2건이었다.
  원문 인용을 복원하는 데는 성공했으나 사용자에게 전달된 답변은 바뀌지 않았다.

실험 3 | IBM 문서의 공식 답변 절 선택 (sections) — 실패
  증상 설명을 인용해도 해결책이 되지는 않으므로, ANSWER·RESOLVING THE PROBLEM
  같은 공식 절을 추출했다. 문서가 다루는 문제와 질문이 일치하는지 확인하고
  모델이 답변 절을 문자로 선택하게 했다. 68건 중 64건은 조건을 만족하는 절이
  없었고, 2건은 유효한 보기를 고르지 못했다. 통과한 2건 중 1건은 Verifier가
  거부했다. 남은 1건은 Packaging Utility 설치 질문(DEV_Q266)이었다.
  응답은 전달됐지만 기술 정답 Judge의 판정은 UNCERTAIN이었다. 오거부는
  48→47건으로 줄었고 정답은 25건에 머물렀다. 답변 한 건을 더 내보낸 것만으로는
  목표를 충족할 수 없다는 사례였다.

실험 4 | 가장 잘 맞는 원문 한 곳에 대한 재판정 (focused) — val_106에서 성공
  여러 보기를 고르거나 JSON을 작성하게 하는 부담을 줄였다. 코드가 Top5에서
  제품·버전·환경과 오류 식별자를 대조하고, 핵심 질문과 표현이 겹치는 답변 절을
  찾았다. 공식 절이 없어도 질문과의 표현 일치도가 높고 구체적인 해결 표현이
  있는 본문은 후보로 삼았다. 가장 잘 맞는 한 곳의 원문과 소속 청크를 보여주고
  “이 구간이 이 조건에서 요청한 답을 직접 뒷받침하는가?”를 YES/NO로 물었다.
  한 곳으로 좁힌 단계는 재판정이다. 실제 답변 생성과 최종 검증에는 기존 Top5를
  그대로 사용했다.
  68건 중 58건은 코드가 적용 가능한 원문 후보를 선택하지 못했고, 7건은 후보가
  있었지만 근거 부족·불확실로 판정됐다. 나머지 3건은 재판정, 생성, Verifier를
  모두 통과했고 기술 정답 Judge에서도 CORRECT였다.

  거부 → 정답으로 바뀐 질문
    TRAIN_Q270  ICWPA1001E 발생 시 클립보드에서 한 번에 1,000명 미만씩 추가하는 우회책
    TRAIN_Q592  Bash 취약점의 WebSphere MQ Hypervisor 영향 여부와 Red Hat 수정 적용
    TRAIN_Q463  WebSphere Portal의 동일 사용자 ID 동시 로그인 제한 기능 유무

  거부 → 비정답 0건, 기존 정답 → 비정답·거부 0건, 불가능 문항의 신규 응답 0건.
  여기서 비정답은 기술 정답 Judge의 PARTIAL, INCORRECT, UNCERTAIN을 포함한다.


4. 전체 비교와 재현 확인

  val_106 방식             Judge 정답/77    오거부/77    불가능 응답/29
  기존 Strict                  25              48               6
  verbatim                     25              48               6
  passages                     25              48               6
  sections                     25              47               6
  focused                      28              45               6

focused의 첫 비교에서는 저장된 Strict 판정을 재사용했다. 이어 같은 검색 캐시로
GPU에서 기존 Judge까지 직접 호출했고, 시간 필드를 제외한 106건의 예측 기록이
모두 일치했다. 이후 검색부터 채점까지 전체 명령을 재실행한 결과에서도 같은
세 문항이 복구됐고, 두 방식의 답변·판정 경로와 문항별 채점이 모두 일치했다.
기본 설정은 재판정 꺼짐이며, focused는 명시적으로 선택하는 실험 옵션이다.


5. 아직 해결되지 않은 부분과 미실행 제안

focused에서도 답할 수 있는 질문 45건을 거부했다. 이 45건만 보면 37건은 코드가
적용 가능한 근거 구간을 선택하지 못했고, 6건은 구간에 대한 재판정에서 멈췄다.
나머지 2건은 재판정 대상이 아니었으며 기존 생성기와 Verifier에서 각 1건씩
거부됐다. 위 58건과 여기의 37건은 각각 재판정 대상 전체와 답변 가능 문항만을
센 수치다. 37건 중 실제로 Top5에 충분한 답이 들어 있는 문항 수는 미확인이다.

다음 후보로 제안한 방식은 기존 CrossEncoder로 질문과 Top5의 각 문단 간 의미
관련성을 계산해, 표현이 달라도 답이 될 만한 문단을 먼저 찾는 것이다. 관련성
점수는 후보 선정에만 쓰고, 원문·적용 조건 확인과 최종 검증은 유지한다.
이 문단 단위 재순위화는 미구현·미평가다. focused의 +3건은 같은 검증 세트에서
여러 방식을 비교해 선택한 결과다. 새 미사용 세트에서 개선이 유지되는지도
별도 검증이 필요하다.
